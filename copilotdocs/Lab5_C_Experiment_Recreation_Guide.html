2. The right reconstruction mindset

Build from stable contracts

Each layer should have a clear input and output:

  1. Geometry: createBox(w,h,d) returns eight homogeneous 3D vertices.
  2. Pose: scara_transforms(joints) returns the world pose of each joint frame.
  3. Projection: a camera's transform_to_image converts 3D points to pixels.
  4. Rendering: drawBox and drawCoord draw projected points.
  5. Interaction: UI changes integer joint values, then the next frame recomputes pose and rendering.

This means a wrong image can be investigated by asking which contract failed: wrong box vertices, wrong transform chain, wrong camera pose, or wrong drawing/UI order.

Use the coordinate-frame diagram mentally

The notation wT2 means “the transform that expresses frame 2 in world coordinates.” A relative transform such as T12 moves from frame 2's parent relationship to the next joint. Chaining is:

wT1 = wT0 * T01
wT2 = wT1 * T12
wT3 = wT2 * T23
wT4 = wT3 * T34

Read multiplication from left to right as a physical story: start in the world, move to the pedestal/joint height, rotate joint 0, travel along link 1, rotate joint 1, travel along link 2, rotate joint 2, then slide and flip the tool.

Keep units explicit

The geometry and kinematics use metres. The CVUI sliders use degrees for j0..j2 and millimetres for j3. get_joints() is the boundary that converts the prismatic slider from millimetres to metres. Camera settings use millimetres internally and convert to metres when building camera matrices.

3. Existing OpenCV foundation

cv::Mat as both matrix and point container

The project represents a 3D homogeneous point as a 4x1 floating-point matrix:

Mat p = (Mat1f(4, 1) << x, y, z, 1);

The final 1 is the homogeneous coordinate. It lets one 4x4 matrix apply rotation and translation together. createHT creates the matrix; transformPoints multiplies every point by it.

Homogeneous transform: createHT

CRobot::createHT(Vec3d t, Vec3d r) accepts translation (x,y,z) and Euler angles in degrees. It converts degrees to radians and constructs the convention Rz(A) * Ry(B) * Rx(Y). The resulting matrix contains a 3x3 rotation, a translation column, and the final homogeneous row.

Do not silently change conventions. The names roll/pitch/yaw and the comments gamma/beta/alpha are tied to this project's matrix formula. If you use a different Euler order, every camera and robot orientation will disagree even if each individual formula looks reasonable.

4. Building the SCARA model

Dimensions and local geometry

The commit defines four file-local constants in metres:

SCARA_LINK_LENGTH    = 0.15f   // 15 cm
SCARA_LINK_SIZE      = 0.03f   // 3 cm square cross-section
SCARA_PEDESTAL_HEIGHT= 0.135f
SCARA_JOINT1_HEIGHT  = 0.15f

create_scara() creates the shapes once. The important design decision is that each movable shape is stored in its own joint frame, rather than permanently transformed into the world. The pedestal is stored in the world frame, link 1 in frame 1, link 2 in frame 2, and the quill in frame 4.

std::vector<Mat> link1 = createBox(SCARA_LINK_LENGTH,
                                   SCARA_LINK_SIZE,
                                   SCARA_LINK_SIZE);
transformPoints(link1, createHT(
    Vec3d(SCARA_LINK_LENGTH / 2, 0.0, 0.0),
    Vec3d(0.0, 0.0, 0.0)));

Because createBox is centered at its origin, shifting by L/2 makes the link extend from its joint origin to the next joint. The quill uses -L/2 on z because the tool tip is defined as the frame origin and the tool body extends upward while tool z points down.

Why model and pose are separated

If create_scara() transformed link vertices using the current sliders, then changing a slider would require rebuilding the geometry. Instead, it stores local geometry once and draw_scara() applies the current transform to a temporary copy every frame. This is the same scene-graph idea used in larger graphics engines.

OpenCV ownership detail: clone before transforming

std::vector<Mat> box;
for (const Mat& pt : _scara_links.at(i))
    box.push_back(pt.clone());
transformPoints(box, base * T.at(link_frame[i]));

OpenCV Mat uses reference-counted data. Copying a Mat object can share its underlying pixels. Since transformPoints mutates its argument, using clone() protects the stored local model from being transformed repeatedly frame after frame.

5. Coordinate frames and forward kinematics

The SCARA chain

TransformTranslationRotationMeaning
wT0zerozeroWorld/pedestal base frame.
T01(0,0,0.15)z by j0Raise to the horizontal arm and turn joint 0.
T12(0.15,0,0)z by j1Travel along link 1 and turn joint 1.
T23(0.15,0,0)z by j2Travel along link 2 and turn the wrist.
T34(0,0,-j3)x by 180°Slide the prismatic joint and point tool z downward.

scara_transforms keeps all five intermediate frames because rendering needs more than the final answer. The array returned is {wT0,wT1,wT2,wT3,wT4}; the drawing code maps pedestal/link1/link2/quill to indices {0,1,2,4}.

Forward kinematics: one output, same chain

fkin multiplies the four moving transforms directly and extracts:

  • x = wT4(0,3), y = wT4(1,3), z = wT4(2,3): translation in metres.
  • theta = atan2(wT4(1,0), wT4(0,0)): heading of the tool x-axis around world z, converted to degrees.
Vec4d CRobot::fkin(Vec4d joints)
{
    Mat wT4 = T01 * T12 * T23 * T34;
    return Vec4d(wT4.at<float>(0,3),
                 wT4.at<float>(1,3),
                 wT4.at<float>(2,3),
                 atan2(wT4.at<float>(1,0), wT4.at<float>(0,0))
                   * 180.0 / CV_PI);
}
Sanity check: with all joints zero, x should be about 0.30 m, y about 0, z about 0.15 m minus the prismatic extension, and the two horizontal links should lie along +x. If this fails, inspect the transform chain before inspecting OpenCV drawing.

6. Controls, animation, and the frame loop

Input boundary

_joint[0..2] hold degree values directly. _joint[3] holds millimetres because that is convenient for a CVUI slider. get_joints() returns Vec4d(j0,j1,j2,j3/1000), keeping kinematics in metres.

update_scara_settings creates four trackbars, Reset, Animate, a board checkbox, and the fkin readout. It calls animate_scara() and then exactly one cvui::update(). Calling CVUI update more than once per frame can break button behavior.

Animation as a state machine

_do_animate is a state number, not a boolean. The sequence is:

1: j0 0 -> 180     2: j0 180 -> -180   3: j0 -180 -> 0
4: j1 0 -> 180     5: j1 180 -> -180   6: j1 -180 -> 0
7: j2 0 -> 360     8: j3 0 -> 150 mm  9/default: reset home

step_toward prevents overshoot with min/max and returns true only when the target is reached. State 7 wraps the displayed j2 slider after +180 because the slider range is -180..180 while the animation needs a full 360° turn.

The per-frame draw sequence

  1. Clear the canvas.
  2. Choose virtual or real projection from _draw_on_board.
  3. If real mode, copy the webcam image and call detect_markers(0).
  4. Require a valid rvec/tvec before drawing onto the board.
  5. Compute joint transforms.
  6. Clone local boxes, transform them, and draw them.
  7. Draw all frame axes and the yellow forward-kinematics tip marker.
  8. Draw the selected camera settings and robot settings.
  9. Show the canvas.

7. Virtual camera and RealCam/ArUco reuse

Virtual camera pipeline

CCameraVirtual stores intrinsic and extrinsic matrices. calculate_intrinsic uses focal length, pixel size, and principal point. calculate_extrinsic represents camera position/orientation. To project a world point, the code inverts the camera-to-world extrinsic, multiplies by intrinsic, then performs the homogeneous divide:

uvw = K * inverse(extrinsic) * point
u = uvw[0] / uvw[2]
v = uvw[1] / uvw[2]

set_default_view(f,x,y,z,roll,pitch,yaw) stores defaults, sets the current controls immediately, disables look-at mode, and recalculates both matrices. In create_scara() it is called with (3,250,-480,203,-101,0,0) so Reset returns to a SCARA-friendly view instead of the earlier Lab 3 view.

RealCam pipeline

The existing CCameraReal API supplies the complete Lab 4 path:

  1. get_image(Mat&) reads one webcam frame.
  2. detect_markers(int) detects ChArUco corners, matches image/object points, and calls solvePnP.
  3. Successful pose estimation stores _rvec and _tvec.
  4. get_rvec() and get_tvec() let Lab 5 check whether a pose exists.
  5. transform_to_image calls OpenCV projectPoints using calibration and distortion coefficients.

Lab 5 deliberately does not duplicate marker detection or camera calibration. It reuses the established functions and adds only the orchestration: webcam background, pose guard, board-alignment transform (180°,0°,90°), and the choice of RealCam projection.

Why the pose guard exists: a webcam frame can exist even when no board has been detected. Without valid rvec/tvec, projecting the robot would produce invalid or misleading points. The UI message “No ArUco board pose yet” makes that state visible.

Board alignment

The board's coordinate convention differs from the robot's desired “z upward from the board” convention. The base transform used in Lab 4 and Lab 5 rotates by (180,0,90). Treat this as a coordinate-convention adapter, not as a robot joint transform.

9. Recreate it yourself: an incremental checklist

  1. Start from the parent commit and confirm Lab 3/4 still render a simple box robot.
  2. Add Lab 5 state in Robot.h: local models, colors, four UI joints, animation state, board flag, and declarations.
  3. Initialize joint values and animation state in init().
  4. Add dimensions and implement create_scara(). Render only the local models at home pose first.
  5. Implement scara_transforms(). Draw coordinate axes at all returned frames; do not add UI yet.
  6. Implement fkin(). Compare its tip to the end-effector frame and a yellow marker.
  7. Implement get_joints() and four trackbars. Verify unit conversion with the pose readout.
  8. Change the draw loop to clone, transform, and render each model every frame.
  9. Add step_toward and animation states. Test one state at a time.
  10. Reuse the RealCam APIs: get frame, detect board, check pose, choose board alignment, project with RealCam.
  11. Add set_default_view to VirtualCam and call it after building the SCARA.
  12. Finally add the Lab 5 menu entry/loop in 7825_Template.cpp and test reset, animation, virtual mode, and board mode.
Suggested verification after every stage: change only one joint, predict the visual result before running, then inspect the axis colors and fkin readout. This turns the program into an experiment rather than a black box.

11. Exercises and next steps

  1. Change link length to 0.20 m and update only the dimension constants. Which parts automatically follow?
  2. Print all five transforms and verify that each translation matches the previous frame plus the next link.
  3. Temporarily draw only the coordinate axes. Can you identify which axis is the tool tip frame?
  4. Replace the animation state machine with a list of target joint vectors and compare the tradeoffs.
  5. Add a unit test for zero joints and a second test for j0=90 degrees.
  6. Use the existing RealCam transform_to_image with one known board-space point and compare it to a hand calculation.
  7. Implement inverse kinematics as the next layer: start by solving the two planar revolute joints, then handle wrist heading and prismatic height.
