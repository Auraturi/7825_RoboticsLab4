  • Build and run, type 6 at the menu. It starts on the virtual camera in joint control, which behaves like Lab 5.
  • Untick Joint Control. Now drag X, Y, Z, Th: the arm follows and the j0–j3 sliders show the answer from ikine().
  • Tick Elbow Flip to see the other solution for the same target (the elbow bends the other way, the tool does not move).
  • Drag X and Y both to the far right. The status line turns red, "Target unreachable", and the arm stays where it last was.
  • Press Animate with Joint Control unticked: the end effector follows four straight lines and leaves a cyan trail. With Joint Control ticked, Animate runs the Lab 5 joint sequence.
  • Reset returns to home and to joint control.
  • Part B (needs webcam, board and marker 50): tick On Board, then Track Mark.

5. Part A-A: the inverse kinematics, derived

Forward kinematics answers "the joints are here, where is the tool?". Inverse kinematics answers "I want the tool there, what should the joints be?". Start from what fkin() computes. Multiplying out the Lab 5 transform chain, with L = 0.15 m (link length) and H = 0.15 m (height of joint 1), gives four plain equations:

x     = L cos(j0) + L cos(j0 + j1)
y     = L sin(j0) + L sin(j0 + j1)
z     = H - j3
theta = j0 + j1 + j2

Seen from above, the SCARA is a 2-link planar arm: j0 and j1 alone decide X and Y. j3 only affects Z, and j2 only affects θ. That is why the problem splits into four small steps.

Step 1: elbow angle j1 (law of cosines)

Square the x and y equations and add them. The j0 terms cancel and only j1 is left:

x² + y² = 2L² + 2L² cos(j1)

cos(j1) = (x² + y² - 2L²) / (2L²)
j1      = ± acos( cos(j1) )

Two things fall out of this one line. If the right-hand side is bigger than 1, the target is farther than 2L = 300 mm and there is no solution. Otherwise there are two solutions, +j1 and −j1: the same hand position with the elbow on either side. The Elbow Flip checkbox picks between them.

Step 2: shoulder angle j0

The direction from the base to the target is atan2(y, x). Link 2 bends the tip away from the line of link 1 by an angle β, so link 1 must point at the target direction minus β:

β  = atan2( L sin(j1), L + L cos(j1) )
j0 = atan2(y, x) - β

atan2 is used instead of atan because it gives the correct quadrant for all signs of x and y.

Step 3: prismatic joint j3

j3 = H - z

Valid only if 0 ≤ j3 ≤ 150 mm, the travel of the quill.

Step 4: wrist angle j2

As the lab suggests, fkin() is reused: call it with the j0 and j1 just found and j2 = 0 to see which way the tool would point, then turn the wrist by the difference.

j2 = theta_target - fkin(j0, j1, 0, j3).theta      (= theta - j0 - j1)

All angles are wrapped back into −180…180° to match the sliders.

6. Part A-B: ikine() in code

Units match fkin() exactly (metres and degrees), so the two functions are inverses of each other: fkin(ikine(pose)) == pose.

bool CRobot::ikine(Vec4d pose, Vec4d& joints, bool elbow_flip)

// j1: law of cosines
double c1 = (x * x + y * y - 2 * L * L) / (2 * L * L);
if (c1 > 1.000001 || c1 < -1.000001)
    return false;                      // out of reach
double j1 = acos(c1);
if (elbow_flip) j1 = -j1;

// j0: direction to target minus the bend
double j0 = atan2(y, x) - atan2(L * sin(j1), L + L * cos(j1));

// j3: from the height
double j3 = SCARA_JOINT1_HEIGHT - z;   // rejected if outside 0 .. 150 mm

// j2: fkin with j2 = 0, then the remainder
Vec4d reached = fkin(Vec4d(j0, j1, 0.0, j3));
double j2 = wrap_180(theta - reached[3]);

It returns bool (the stub in Robot.h hinted at that): true and fills joints, or false and leaves joints alone. The tiny 0.000001 tolerance exists because the home pose is exactly at full stretch, where float rounding can push cos(j1) to 1.0000001.

7. Part A-C: how the GUI ties fkin and ikine together

draw_scara_lab6() draws the robot, then calls update_scara_settings_lab6(), which works in one of two directions each frame:

Joint Control tickedJoint Control unticked
Inputj0–j3 sliders (_joint[])X Y Z Th sliders (_pose[])
Calculationfkin(get_joints())ikine(pose, joints, _elbow_flip)
Output shown onX Y Z Th slidersj0–j3 sliders, via set_joint_sliders()
Animate runsanimate_scara() (Lab 5)animate_scara_ikine() (Lab 6)

Either way the result ends up in _joints_lab6, and that is what the robot is drawn from, using Lab 5's scara_transforms(), transformPoints(), drawBox() and drawCoord().

Why a separate _joints_lab6? The Lab 5 joint sliders are whole numbers (degrees, mm). Rounding an ikine answer to whole degrees would move the tool by up to about 2.5 mm at full reach, and the straight-line animation would wobble. So the exact answer is kept as doubles for drawing, and the int sliders only display it.

Unreachable targets: _ik_ok goes false, _joints_lab6 is not updated (the arm holds its last good pose), and the status line shows "Target unreachable" in red. The yellow circle still shows where the target is.

Switching modes smoothly: while in joint control, the pose sliders are continuously filled from fkin and Elbow Flip is set to match the sign of j1, so unticking Joint Control does not make the arm jump.

8. Part A-D: straight-line animation

animate_scara_ikine() uses the same state-machine idea as Lab 5's animate_scara(): _do_animate is which move is running and _anim_count is the step within it. The difference is what gets stepped. Lab 5 stepped the joints. Lab 6 steps the target pose in a straight line and lets ikine find the joints every frame:

t    = _anim_count / IK_ANIM_STEPS            // 0 → 1 over 60 frames
pose = _anim_start + (target - _anim_start) * t   // linear interpolation

There are four moves through the IK_WAYPOINTS table (approach, straight across at constant height, out-and-down while turning the tool 90°, and back). The joints move in curves so that the tool moves in a line, which is the whole point of inverse kinematics. A cyan trail is drawn from fkin() of each ikine answer, so the trail shows where the tool really went, not just where it was asked to go.

9. Part B: tracking marker ID 50

Part B-A: robot on the board

The On Board checkbox does what Lab 5's "Draw on ArUco board" did, with the same steps and the same board alignment createHT((0,0,0), (180,0,90)). In joint control the Animate button still runs the Lab 5 joint animation.

Part B-B: marker pose

About estimatePoseSingleMarkers: the lab names this function, but it is not in the OpenCV 4.10 build supplied for the course (it lives in the separate contrib module since 4.7). CCameraReal::detect_single_marker() does the same thing the same way: ArucoDetector::detectMarkers finds the four corners of marker 50, then solvePnP solves for the pose given the marker's known size. This is the approach already used for the board in Lab 4.

solvePnP returns rvec and tvec. rvec is an axis-angle vector, not a rotation matrix: its direction is the rotation axis and its length is the angle. createHT_rvec() calls Rodrigues() to convert it into a 3×3 rotation matrix and packs it with tvec into the usual 4×4 transform.

The camera reports both poses relative to itself. To get the marker relative to the robot, chain the transforms (read right to left, like Lab 2):

cTb = board  in the camera frame      (from detect_markers, Lab 4)
cTm = marker in the camera frame      (from detect_single_marker)
bTw = robot world in the board frame  (the board alignment, called "base")

bTm = inv(cTb) * cTm       marker in the board frame  → used to draw the yellow box
wTm = inv(bTw) * bTm       marker in the robot frame  → used for ikine

X, Y, Z are the last column of wTm. Roll, pitch, yaw are pulled out of its rotation part using the same Rz·Ry·Rx order that createHT() builds, so they mean the same thing as everywhere else in the program. They are printed at the bottom left.

The yellow box is createBox(30 mm) moved by bTm and shifted half a cube down, because the marker is printed on the top face of the paper cube.

Part B-C: locking the robot on

track_marker() ends by copying the marker's X, Y, Z and yaw onto the _pose[] sliders (clamped to the slider ranges). Ticking Track Mark also forces On Board on and Joint Control off, so update_scara_settings_lab6() runs ikine on those sliders exactly as if you had dragged them. No special tracking path was needed: the marker is just another hand on the sliders.

11. Things to check when you have the board

  • Marker size. MARKER_SIZE = 0.021f and MARKER_BOX_SIZE = 0.03f near the top of the Lab 6 section were measured off the PDF page, not a printout. Measure the black square with a ruler. If the size is wrong, the marker will appear too near or too far.
  • Marker ID and dictionary. The code assumes the cube markers are from DICT_6X6_250, the same as the board. If "Marker 50 not found" stays up with the cube in view, this is the first thing to check.
  • Reach. The robot stands on the board origin and reaches 300 mm. Beyond that you get "Target unreachable".
  • Height. The target is the marker itself (top of the cube, about 30 mm up). Pose noise in Z is a few mm; Z is clamped at 0 so a marker lying flat still tracks.
